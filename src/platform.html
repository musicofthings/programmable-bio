Platform

LabOS — the layer between the model and the bench

A design model emits candidates. A robotic instrument executes programmes. LabOS is everything in between: the part that turns an intent into an executable run and turns a run back into data a model can learn from.

Architecture

Five components, one loop

Protocol compiler

Takes a described experiment — plain language, a construct file, or a structured API job — and lowers it into an executable instrument programme. This is the piece that replaces a technician re-typing a Word document, and it is where reproducibility is actually won.

Feasibility & quote agent

Answers, at submission time, whether the current fleet can run the protocol and what it will cost. Returns runnable, runnable-with-substitutions, or out-of-scope-because. Removes the multi-week quoting cycle that defines legacy CRO engagement.

Scheduler

Packs incoming orders across instruments and shifts to maximise utilisation. Instrument capacity is a fixed cost, so utilisation is gross margin — which makes the scheduler the most commercially consequential component in the system.

QC & anomaly agent

Watches controls and instrument telemetry mid-run. A failed plate is caught and re-queued while the reagents are still on deck, rather than surfacing as a disappointing result three weeks later.

Provenance signer

Every result is signed with the instrument identity, reagent lots, calibration state, and the exact programme executed. When a finding is challenged, the record of what physically happened is retrievable rather than reconstructed.

The experimental graph

All of the above accumulates into a typed graph linking hypothesis, execution, and outcome. Serving customers well and building the data asset are the same activity.

Design principle

Every run is a training example

Most lab software is built to produce a report for a human. LabOS is built to produce a record for a model. The difference shows up in what we keep:

  • Negative results are first-class — a candidate that failed to bind is returned with the same fidelity as one that succeeded, because that is exactly the label a design model is missing
  • Parameters are structured, not prose — conditions are typed fields, so runs are comparable across time and instrument
  • Raw and parsed both persist — re-analysis never requires re-running the experiment
  • Failure modes are labelled — an expression failure and a binding failure are different data, and conflating them destroys the signal
This is why the loop closes. A conventional CRO returns an answer. LabOS returns an answer plus the structured evidence needed to improve the model that asked the question.

Scale-out

The software layer is the durable asset, so it gets built first. Running early volume through partner wet labs proves demand and pricing before committing instrument CapEx — and the protocol compiler that drives a partner lab is most of the compiler that will drive an owned one.
